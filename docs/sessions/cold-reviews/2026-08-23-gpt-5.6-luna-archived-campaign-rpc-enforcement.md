# Archived Campaign RPC Enforcement Review — GPT-5.6 Luna

## Overall assessment

**Verdict: the plan is strong and directionally correct, but I would not approve it unchanged.** The core design achieves the stated invariant for the six explicitly identified write surfaces, and the scope discipline is unusually good. The main weakness is that the plan is more confident than its stated verification basis warrants about the completeness of the write-path inventory and about the exact safety properties of the proposed RLS helper.

The most important change I would request before implementation is a **systematic, independently reproducible write-surface inventory** and a corresponding regression matrix. The plan already acknowledges that its inventory is not exhaustive; because the stated goal is "every DM-write path", that is the central correctness question, not a secondary reviewer note.

## 1. Does the plan achieve its stated goal?

**Yes, if the six-path inventory is complete and the proposed SQL matches the verified repository state.**

The plan correctly identifies two different enforcement mechanisms:

- RPC-mediated mutations should perform an explicit archive-state assertion after establishing caller authority.
- Direct column updates need an RLS predicate that incorporates both DM authority and active-campaign state.

That distinction is important. Reusing `is_campaign_dm()` for the new write restriction would be wrong because the same predicate supports reads, and archived campaigns are intentionally still browsable.

The ordering of the RPC check is also sensible: authority first, archive-state second. That avoids exposing archive state to callers who are not already authorised for the campaign.

The central reusable `assert_campaign_active()` is a reasonable abstraction. It makes the invariant explicit and gives future RPCs a straightforward mechanism to adopt it.

However, the stated goal is broader than "these six known paths". It says every DM-write path that can mutate campaign settings or bound-character state must be rejected. The plan itself admits that its six-path discovery was based on a targeted grep rather than an exhaustive review. Consequently, **the plan achieves the goal only conditional on that inventory being complete**.

## 2. Are any "Verified" facts actually shaky?

Most of the listed facts are appropriately labelled as verified because the plan says they were read directly from the repository. I would nevertheless distinguish between **verified observations** and **verified conclusions**.

The strongest examples are:

- "`campaigns.archived_at` exists" — concrete and appropriately verified.
- The absence of RPCs named `set_ignore_player_ap` and `set_campaign_rules` — also concrete and testable.
- The existence of a direct column-level grant and `campaigns_update` RLS policy — concrete.
- The listed RPCs existing and being DM-gated — concrete if the source inspection really covered their definitions.

The shaky part is the implicit conclusion that the inventory is complete. The plan explicitly says the grep was not an exhaustive manual read. That should not sit under a heading implying that the resulting inventory is verified.

In particular, these should be treated as **provisional until independently checked**:

1. That there are exactly five relevant DM RPCs.
2. That there are no direct writes to related tables which can mutate campaign/character state.
3. That no `SECURITY DEFINER` function indirectly invokes one of the relevant mutations while bypassing the proposed guard.
4. That no trigger, view, stored procedure, RPC alias, or grant creates another DM-controlled write route.
5. That the direct `campaigns` grant really is limited to the two columns described.

The plan already identifies "no other write path exists" as an assumption, which is good. I would move the **entire completeness claim** out of the Verified section until the second inventory pass has happened.

## 3. Is there a better alternative?

**Not materially better than the proposed approach, assuming the inventory is correct.**

I agree with rejecting modification of `is_campaign_dm()`. That would conflate read access with write permission and undermine the intended "browsable but frozen" semantics.

I also agree that a generic trigger is not obviously superior. A trigger could provide a hard backstop, but it would have to reconstruct enough context to distinguish DM administrative writes from legitimate player writes. That introduces complexity into a security boundary without eliminating the need to reason about authorisation.

There is, however, one alternative worth considering as a defence-in-depth question:

### A database-level invariant trigger

A carefully designed trigger on the affected tables could make it impossible for an archived campaign to be mutated regardless of which RPC or direct SQL route is used. But this is only attractive if the data model makes the distinction between administrative and player writes cleanly available. The plan explains why that distinction is currently problematic, so I would **not choose the trigger approach simply for DRYness**.

The better improvement is therefore not a different architecture; it is **stronger inventory and testing around the existing architecture**.

One small design refinement: rather than having the RLS helper duplicate archive-state lookup logic independently of the assertion helper, the project could document the two helpers explicitly as having different contracts:

- `assert_campaign_active()` = procedural guard that raises.
- `is_campaign_dm_and_active()` = boolean predicate suitable for RLS.

That makes the intentional duplication of the underlying condition clearer and reduces the risk that a future maintainer "simplifies" the RLS function into an unsafe form.

## 4. What's missing?

### A. A stronger write-path inventory

This is the biggest gap.

Before writing the migration, the reviewer should require a repeatable inventory covering at least:

- all `SECURITY DEFINER` functions that can mutate `campaigns`, `characters`, or related campaign-bound state;
- all `INSERT`, `UPDATE`, and `DELETE` grants for DM-accessible tables;
- all RLS policies permitting DM/co-DM writes;
- all functions containing `is_campaign_dm()` or `is_campaign_owner()`;
- functions that call another mutating function rather than containing the mutation directly;
- triggers on the affected tables;
- column-level grants, not only table-level grants.

The plan mentions rerunning a grep, but a grep for function definitions plus DM predicates is not enough to establish the complete write surface.

### B. Tests for authorised and unauthorised states

The proposed tests cover a DM and archived/unarchived campaign. They should also explicitly prove that:

- a non-DM cannot use the new helpers to infer or alter archive state;
- the owner can still unarchive;
- an archived campaign remains readable by an authorised DM;
- an unarchived campaign continues to permit the same writes as before;
- a DM of Campaign A cannot mutate Campaign B by supplying Campaign B's UUID/character ID;
- `dm_unbind_character()` is blocked only when the character belongs to the archived campaign, if that is the intended semantics.

### C. Direct SQL/RLS testing beyond the named column update

The direct `campaigns.update({ignore_player_ap: true})` test is good, but it should test **both** `ignore_player_ap` and `rules`, because the plan identifies both as the direct-write surface.

It should also test that the policy cannot be bypassed by updating some other campaign column if the grant/policy configuration changes later.

### D. Behaviour of NULL/nonexistent campaigns

The helper's intended behaviour should be made explicit.

For an unknown campaign UUID, `assert_campaign_active()` does not raise the archive error because the `exists` condition is false. That is probably correct because the existing authority check should reject the caller first. The tests should nevertheless verify that error ordering remains as intended.

### E. Concurrency / archive race

The plan does not discuss a race between:

1. the RPC checks that a campaign is active; and
2. another transaction archives the campaign before the actual mutation commits.

Whether this matters depends on how `archive_campaign()` and the mutation functions transact and lock rows. If the requirement is a strict database invariant — "no write can commit against an archived campaign" — then merely checking `archived_at` at an earlier statement is potentially weaker than a commit-time invariant.

This is the most important technical risk that is not currently named.

If PostgreSQL's normal row-level locking or the specific function implementations already make the race impossible, the review should say why. If not, the project needs to decide whether "checked before mutation" is sufficient or whether the archive transition must coordinate with writes.

The RLS policy has the same conceptual issue: RLS predicates are evaluated during the statement, not magically as a global serialisation mechanism.

## 5. Is Verification objectively checkable?

**Mostly, but not yet as strongly as it should be.**

The good part is that the plan gives concrete operations and expected outcomes rather than saying "test that it works". The direct signed-in RPC calls are particularly good because they bypass the UI.

However, "run `get_advisors` and skim `get_logs`" is not by itself an objective correctness test. Those checks can identify certain deployment or security issues, but they cannot establish that the archive invariant covers every write path.

Likewise, "confirm each is rejected" is objectively checkable for the five listed RPCs, but does not prove completeness.

I would change verification into a small explicit matrix:

| Scenario | Expected |
|---|---|
| DM + archived + `award_ap` | Reject |
| DM + archived + `award_gold` | Reject |
| DM + archived + `declare_downtime` | Reject |
| DM + archived + `dm_edit_character_log` | Reject |
| DM + archived + `dm_unbind_character` | Reject |
| DM + archived + update `ignore_player_ap` | Reject |
| DM + archived + update `rules` | Reject |
| DM + archived + read campaign | Allow |
| Owner + archived + `unarchive_campaign()` | Allow |
| DM + active + all six write surfaces | Allow |
| Non-DM + archived + relevant writes | Reject for existing authority reason |
| DM + Campaign A + attempt to mutate Campaign B | Reject |

Then separately perform the **write-surface inventory test** and attach its results to the review/PR.

That would make the verification substantially more independent of the author.

## 6. Should the plan split?

**I would keep the core migration together and keep the invitation subsystem out of it.**

The current scope boundary is defensible.

The five RPCs and the `campaigns_update` policy all implement the same invariant — **DM writes must not mutate an archived campaign** — and shipping them together gives one coherent security property.

`character_dm_notes` is different because its current `FOR ALL` policy couples read and write permissions. Correctly hardening it requires changing the policy shape so archived notes remain readable while writes are blocked. That is a meaningful additional design change and deserves its own migration/review.

The invitation subsystem should definitely remain separate. The plan gives a good reason: it has recently undergone its own security hardening, and reopening it unnecessarily increases review scope.

I would therefore structure the work as:

**Now**
- Five DM mutation RPCs.
- `campaigns_update` direct-write policy.
- Comprehensive write-path inventory.
- Tests for archived/read/unarchived behaviour.
- Documentation/changelog updates.

**Later**
- Split `character_dm_notes` into read/write policies and decide whether archived-note writes should be frozen.
- Independently evaluate invitation mutations against the archive invariant.

## Additional observations

### The `dm_unbind_character()` decision deserves elevation

The plan currently lists blocking `dm_unbind_character()` as an assumption. Because this is the one proposed change that could plausibly conflict with a legitimate administrative recovery workflow, I would resolve that question **before migration**, not leave it as a reviewer flag.

If unbinding is needed to recover a character from an archived campaign, then "archived = completely frozen" has an intentional exception and the invariant should say so explicitly. If it is not needed, block it.

### The error contract should be considered

The plan proposes a specific exception:

`This campaign is archived and read-only`

That is useful for humans, but the review should consider whether callers depend on exception text. If the client currently treats archive state specially, a stable SQLSTATE or documented error code would be more robust than relying solely on message text.

This is not necessarily required for the fix, but it is worth deciding before establishing the error as an API contract.

## Final recommendation

**Approve with changes.**

The architecture is sound: preserve read access, keep existing authority checks, add an explicit active-campaign guard to administrative RPCs, and tighten only the write RLS policy rather than corrupting the shared DM predicate.

The critical prerequisite is to turn the current "six paths found by targeted grep" into a **demonstrably complete write-surface inventory**. The second priority is to address or explicitly rule out the archive/write concurrency race.

If those two points are resolved, the proposed single migration is appropriately scoped and preferable to splitting the core fix into multiple changes. The separate treatment of `character_dm_notes` and the invitation subsystem is sensible and should remain.
