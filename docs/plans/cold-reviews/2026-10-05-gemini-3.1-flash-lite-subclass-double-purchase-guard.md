### 1. Does this achieve the goal?
**Verdict: YES.**
The design successfully implements a "first-purchase wins" guard, prevents double-billing, and provides the necessary UI warnings. By utilizing `_abilDoor` to track precedence and mirroring the identification via `abilityIdent`, the proposal effectively bridges the two collections in `compute()`. The inclusion of `purchaseLegality` ensures that the UI tools will reject subsequent duplicate purchases before they are ever committed to the event log.

### 2. Are any assumptions shaky?
**Verdict: MEDIUM.**
The assumption that "no saved character has a legitimate reason to hold the same ability through both doors" is the biggest risk. While it is likely true for current gameplay, RPG character builders often have users who perform manual edits or recover broken logs. If a legacy character was legitimately trying to force two copies (e.g., as a workaround for a missing feature), this change will retroactively suppress one, potentially changing their build stats unexpectedly.

### 3. Is there a simpler or safer alternative to the stamped `_abilDoor`?
**Verdict: NO.**
Given that `compute()` is a pure function that cannot inspect the event history (log) and cannot be signature-changed without massive downstream refactoring, stamping state on the `build` object is the most pragmatic way to communicate the "first-purchase" intent. Alternative solutions (like scanning the entire log from within `compute()`) would require a total rewrite of the engine's data flow.

### 4. Is leaving ownership sets unchanged correct?
**Verdict: YES.**
This is correct. Since the goal is to treat the duplicate as "not counted" but still "owned," maintaining the existing ownership sets ensures that feature-label-keyed logic (prerequisites, effect triggers) remains consistent with the character's status as a possessor of that ability.

### 5. Is routing the refusal through `purchaseLegality` sound?
**Verdict: YES.**
Routing the refusal through `purchaseLegality` is standard and safe, as it prevents the duplicate event from ever entering the `foldBuild` history. This ensures that the event log remains "clean" (i.e., it doesn't contain a second, invalid purchase event that the engine has to handle as a special case).

### 6. What is missing or wrong in the diff?
**Verdict: LOW.**
The logic in `compute()` (lines 515–518) creates an `_byId` map to deduplicate. This assumes that `DATA.subAbilMap` is complete and accurate relative to `DATA.features`. While the document claims this is verified, if any subclass ability key exists in the log that is *not* currently in the `subAbilMap` (due to legacy rename/deprecation), the `_byId` lookup might miss it. Additionally, the `_dupSubKey` mapping could be fragile if `_byId` is overwritten by multiple entries (though the logic suggests a 1-to-1 mapping for these specific keys).
