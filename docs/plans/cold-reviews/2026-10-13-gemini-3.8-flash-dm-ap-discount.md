# dm-ap-discount-review-gemini-2.5-pro.md

## 1. Overall Assessment (Logic, Clarity, Scope, and Risk)

*   **Logic (B+):** Modeling a discount as purchase-bound *income* (adding to `earned` rather than mutating `spent` downward) is a clever fit for the project's invariants. It preserves the append-only rule, keeps Track-Level math intact without rewriting `earnedWithDm()`, and naturally cleans up if the target purchase is bought off. However, the interactions between creation lock, creation ceiling, and 100% discounts introduce serious UX edge cases during character generation.
*   **Clarity (A-):** The document is concise, well-structured, and explicitly states constraints, existing architecture, and verified codebase facts.
*   **Scope (A):** Scoped tightly. It resists feature creep by explicitly deferring gold/downtime discounts, wizard scribing, and purchase-granting to follow-up tasks.
*   **Risk (B):** High risk of subtle regression across the ~65 call sites reading economy helpers. The database ledger parity and trigger protections are viable but need rigorous enforcement.

## 2. Answers to Specific Questions

### Does this plan achieve the goal?
**Yes, with caveats.** It provides a mechanism for a DM to apply full or partial discounts tied directly to specific purchases, tallies them, ensures the discount disappears if the purchase is revoked, and satisfies Owner Decision B1. The core goal is met.

### Are any of the assumptions shaky?
1.  **"Percentages are converted to a whole AP amount when the DM saves, so the log only ever stores AP":** This assumption lacks an explicit rounding specification (e.g., standard round vs. floor vs. ceil). On odd point costs (e.g., a 25% discount on a 7 AP trait = 1.75 AP), client UI ambiguity could cause discrepancies or allow 0-AP no-op events.
2.  **"No existing log contains an event type named `dmDiscount`":** Likely safe, but assuming it instead of running a one-line SQL query across the 35+ live rows before finalizing the document is unnecessary guesswork.

### Is there a better alternative?
No better architectural alternative exists given the constraints.
*   Mutating past `cost` violates the core append-only invariant.
*   Lowering `spent` breaks B1 (Track-Level and creation lock calculations depend on full price).
*   Using unbound `award` events causes the exact bookkeeping leak this task is designed to fix.
Treating the discount as an earned rebate locked to a target `seq` is the cleanest pattern available.

### What is missing?
1.  **DM Correction/Revocation Mechanism:** Events with `dmEdit: true` act as "undo barriers." If a DM makes a mistake (e.g., discounts the wrong ability or typos the amount), how is the discount revoked? Does a second discount allow negative values, is there a `dmRemoveDiscount` event, or is the DM forced to perform manual DB intervention?
2.  **Rounding Rules:** Explicit formula for percentage-to-AP conversion.
3.  **Multiple Discounts on One Target:** The plan states "existing discounts plus this one must not exceed its cost," implying cumulative discounts are permitted. The engine fold algorithm must explicitly state whether it sums discounts by `targetSeq` and caps the aggregate sum at `target.cost`.
4.  **Audit Scope for 65 Call Sites:** While mentioned as needing a "decision record," auditing and potentially updating 65 call sites across three separate HTML/JS tools is a major migration effort. It needs a clear testing strategy so displays do not show mismatched numbers.

### Is the Verification section objectively checkable?
**Mostly yes.** "Engine parity test: 0 failed", "expected-results.csv is unchanged", "replay of every live character shows identical earned, spent, and available", and "database advisor shows no new findings" are binary, automated, and checkable.
*What is weak:* "The end-to-end DM Console → Live Sheet test passes" needs explicit test criteria detailing whether it verifies UI string formatting, edge cases (cancellations), or live database interactions.

### Should this be split into more than one plan?
**No, but execution should be staged.** The scope is cohesive: engine model + DB validation + UI representation. Splitting it would leave the database or UI in an inconsistent half-state. However, the audit of the ~65 UI call sites should be done in a dedicated sub-pass after the engine and SQL tests pass.

## 3. Analysis of Risks

### Risk 1 (Creation Ceiling vs. Lock — Owner Decision F1)
**Flagged UX Concern:** Under F1, the creation ceiling expands by the discount amount, but the creation lock triggers strictly on `apValue` (`spent` full price).
*The Problem:* If a DM awards a 100% discount on an expensive item during character creation (e.g., a 40 AP signature racial trait), that 40 AP immediately counts toward the lock threshold. A character whose player has actually spent 0 of their starting budget could have their character prematurely locked in CharGen because the full AP value hit the threshold.
*Recommendation:* Re-evaluate whether `creationLockState()` should check `spent` or `apPaid`. If it remains on `apValue` per B1, CharGen must clearly alert the player why they are locked despite having unspent creation budget.

### Risk 2 (Database Sum without Cancellation)
**Opinion:** Accepting divergence between the SQL ledger check (`pact_ap_ledger_spend`) and engine active-event resolution is acceptable *only* as a temporary, non-blocking check, because the server is being more permissive rather than falsely rejecting valid saves.
However, this creates a subtle hole: if a player client has a bug or is modified, it could exploit that "ghost" income from bought-off discounts to overspend on future purchases.
*Recommendation:* If implementing recursive/referential target cancellation in SQL is too heavy, keep it as-is, but add a database assertion or periodic health check script that alerts when `pact_ap_ledger_spend` diverges significantly from the engine's fold of the log.

### Risk 3 (Non-DM Appending `dmDiscount`)
**Opinion:** This is a hard security requirement.
*Recommendation:* Do not rely merely on the award trigger. In Supabase/Postgres, ensure that the row-level update trigger on the characters table checks the log delta. If any new event in the delta has `type = 'dmDiscount'`, the transaction must abort unless executed within the security context of `dm_edit_character_log` (or with `dmEdit: true` signed/verified by DM authorization). This must be covered by a negative unit test attempting to append `dmDiscount` via the player's standard update path.
