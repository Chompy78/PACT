# subclass-double-purchase-guard-review-Nemotron 3 Super.md

## (1) Does this achieve the goal?
**Verdict:** Yes, the design achieves the stated goal under the verified assumptions.  
The proposal ensures that when an ability is acquired through both doors, only the first purchase is counted (with AP applied once), the second purchase triggers a single ⛔ warning (which `purchaseLegality` treats as a hard refusal), and the duplicate is listed once under "Blocked purchases". The Live Sheet UI correctly reflects ownership via `ownsAbility()`, and the stamped order (`_abilDoor`) enforces P3 (first door wins) without altering price rules. The verification notes confirm that all 192 abilities are refused as duplicates in both orders, and the engine-parity fixtures pass. However, this relies on the assumption that no saved character legitimately requires holding the same ability through both doors (which is explicitly assumed but not proven), and that the stamped order remains consistent across all flows (addressed in risks).  

**Finding:** The design meets the goal if assumptions hold.  
**Rank:** MEDIUM (certainty: likely) – because while the logic appears sound, the assumption about no legitimate dual-door ownership is unverified and could cause edge-case failures in saved characters.

## (2) Are any assumptions shaky?
**Verdict:** Yes, several assumptions are shaky and introduce risk.  
The document assumes: (a) nothing else reads purchase order across collections (unproven), (b) stamping order on `build._abilDoor` is safe during undo/time-travel/draft flows (risky, as noted in Risks), (c) treating the later copy as "not counted" but still "owned" is correct for effects (questionable if effects key on the *exact* purchase event rather than logical ownership), and (d) no saved character has a legitimate reason to hold the same ability through both doors (contradicted by the real campaign example where it happened, though deemed erroneous). The assumption about stamp persistence is particularly fragile: if a build is modified via direct log editing (bypassing MUT) or loaded from an old save lacking `_abilDoor`, the fallback to door A may incorrectly count the feature copy as duplicate when the subclass copy was actually first (or vice versa), violating P3.  

**Finding:** Assumptions about order persistence and lack of legitimate dual-door use are shaky.  
**Rank:** HIGH (certainty: likely) – the real campaign incident proves dual-door purchases occur, and the stamp’s vulnerability to missing/stale state directly threatens correctness.

## (3) Is there a simpler or safer alternative to the stamped `_abilDoor`?
**Verdict:** Yes, a simpler alternative exists: derive order in `compute()` by scanning the event log (despite the document’s objection).  
The document rejects scanning the log in `compute()` because it "receives a build, not the log," but the build is derived from the log via `foldBuild` (stated in Context). Since `compute()` already has access to the full build (which includes the log indirectly through replayed state), it could reconstruct purchase order by checking the sequence of `subabil` and `feature` events in the log *if* the log were attached to the build object. However, the document states that a character is an "append-only event LOG" and the build is derived by replaying it, implying the log is external to the build object. A safer alternative would be to store the order in the log itself (e.g., as a metadata tag on purchase events) and have `compute()` accept the log as an argument—but this changes the API. A truly simpler API-preserving solution: during `compute()`, iterate over `b.subAbilities` and `b.features` in a fixed order (e.g., features first) and mark the first occurrence as canonical, but this violates P3 (which requires honoring actual purchase order, not a fixed door preference). Thus, no simpler *API-preserving* alternative satisfies P3 without stamping, but the stamping approach could be made safer by persisting the order in the log (e.g., adding a hidden field to purchase events) rather than on the transient build object.  

**Finding:** No simpler API-preserving alternative satisfies P3, but stamping on the build object is riskier than persisting order in the log.  
**Rank:** MEDIUM (certainty: guess) – the objection to log-scanning assumes the log isn’t accessible, but Context implies it is the source of truth; however, without seeing `foldBuild`, we cannot confirm if the log is attached to the build.

## (4) Is leaving ownership sets unchanged correct?
**Verdict:** Yes, leaving `_ownedFeatSet` and `_blockedFeat` unchanged is correct and necessary.  
The document correctly argues that adding the duplicate to `_blockedFeat` would incorrectly remove the logical ownership (since the ability is still owned via the counted copy), breaking effects keyed on the feature label (e.g., prerequisites for other features). By leaving ownership sets untouched, the counted copy’s ownership persists, ensuring effects apply exactly once. The warning and "Blocked purchases" listing merely reflect the duplicate’s non-contribution to AP without altering the ownership state. This aligns with P3: the first purchase confers full ownership, and the second is a redundant acquisition with no additional effect. The verification that Live Sheet uses `ownsAbility()` (which checks both doors) further confirms ownership is correctly represented.  

**Finding:** This aspect of the design is sound and critical for correctness.  
**Rank:** LOW (certainty: certain) – the reasoning is explicit and matches the owner’s intent (P3) without introducing side effects.

## (5) Is routing the refusal through `purchaseLegality` sound?
**Verdict:** Yes, routing refusal through `purchaseLegality` is sound and leverages existing infrastructure.  
Since `purchaseLegality` already blocks purchases that introduce new ⛔ warnings (treating them as hard refusals unless soft-listed), and the design ensures the duplicate generates exactly one such warning, the tool UI will automatically refuse the second purchase without additional logic. This avoids duplicating refusal checks in the pickers and maintains consistency with other validation (e.g., budget limits). The document notes that both tools call `purchaseLegality` at buy time, so the guard integrates seamlessly. The only risk is if the warning text collides with another ⛔ warning (addressed in Q6), but the mechanism itself is appropriate.  

**Finding:** This approach is efficient and reuses proven validation pathways.  
**Rank:** LOW (certainty: certain) – it adheres to the principle of least change and uses the existing refusal pipeline.

## (6) What is missing or wrong in the diff (cite lines)?
**Verdict:** The diff contains a subtle bug in the duplicate detection block (lines 509-520) that risks double-warning or incorrect ordering under specific conditions.  
Specifically, in the feature loop’s duplicate handling (lines 515-522), the warning text uses `_dupSubKey[lab]` to fetch the subclass key for the message. However, `_dupSubKey` is populated in the detection block (lines 509-520) only when an ability exists in both collections. If the counted copy (per `_abilDoor`) is the feature copy (i.e., `_abilDoor[id] === 'f'`), then the duplicate is the subclass copy, and `_dupSubKey[lab]` correctly points to the subclass key. But if the counted copy is the subclass copy (`_abilDoor[id] === 's'`), the duplicate is the feature copy, yet the code still uses `_dupSubKey[lab]` (which was set under the assumption that the duplicate is the subclass copy) to generate the warning. This would cause the warning to incorrectly reference the subclass key when the duplicate is actually the feature copy, breaking message accuracy. For example, if a feature purchase comes first (stamping `_abilDoor[id] = 'f'`), then a subclass purchase later, the detection block marks the subclass key as `_dupSub` (line 518: `_dupSub.add(_byId[_id])`). When processing the subclass loop later (lines 548-560), the duplicate handling (lines 552-562) correctly uses `a.name` and `a.cls` for the warning. However, when processing the feature loop (lines 500-540), the duplicate handling for the feature copy (which is the *counted* copy in this scenario) should not trigger—only the *later* copy (subclass) should be duplicated. The error arises because the detection block unconditionally assigns `_dupSubKey` based on `b.subAbilities`, assuming the duplicate is always the subclass copy when the feature is counted first, but reverses the logic when the subclass is counted first. The warning text in the feature loop’s duplicate block (lines 515-522) is only executed when the feature copy is the *duplicate* (i.e., when subclass was counted first), so `_dupSubKey[lab]` is valid in that context. However, the symmetric issue exists in the subclass loop’s duplicate block: it does not use a parallel `_dupFeatKey` map, instead relying on `a` from `DATA.subAbilMap[key]` (which is always available). A closer look reveals the detection block sets `_dupSubKey[id] = _byId[id]` (the subclass key) and then conditionally adds to `_dupSub` or `_dupFeat` based on `_abilDoor`. In the feature loop duplicate block, when the feature is the duplicate (subclass counted first), `_dupSubKey[id]` is the subclass key—correct for the warning. In the subclass loop duplicate block, when the subclass is the duplicate (feature counted first), it uses `a` (from `DATA.subAbilMap[key]`) to get the subclass name/class—also correct. Thus, the warning text appears accurate. However, a more critical issue is missing: the detection block does not guard against Hit-Dice blocking the counted copy when generating the warning for the duplicate. The feature loop duplicate block checks `if(!(hd<requiredHD(_ka)))` before adding to `blockedAP` and `_BLI` (line 521), but the subclass loop duplicate block lacks this check (line 556: `if(!_blockedFeat.has(a.cls+": "+a.name))` only checks feature blocking, not HD blocking of the counted subclass copy). If the counted subclass copy is HD-blocked, the feature duplicate should not be listed a second time (per the design), but the subclass loop duplicate block does not verify HD status of the counted feature copy (it checks `_blockedFeat.has(a.cls+": "+a.name)`, which is feature blocking, not HD). This could cause duplicate warnings to appear twice if the counted copy is HD-blocked but not feature-blocked.  

**Finding:** The subclass loop duplicate block (line 556) fails to check HD blocking of the counted feature copy, risking duplicate "Blocked purchases" entries when the counted copy is HD-blocked but not feature-blocked.  
**Rank:** HIGH (certainty: likely) – the text explicitly states: "If the counted copy is itself blocked by a Hit-Dice requirement, do not list the duplicate a second time," but the subclass loop omits this check.

## (8) Should this be split?
**Verdict:** No, splitting the changes would increase risk and complexity without clear benefit.  
The proposal touches interconnected systems: ownership helpers (`abilityIdent`, `ownsAbility`), mutation stampers (`MUT.feature`, `MUT.subabil`), compute logic (duplicate detection and warning), and UI rendering (`ownsAbility` in Live Sheet). Splitting (e.g., adding helpers first, then stamping, then compute changes) would create intermediate states where:  
- Helpers alone change nothing observable (safe but useless).  
- Helpers + stamping without compute changes would stamp `_abilDoor` but not act on it, leaving the duplicate-charge bug intact.  
- Helpers + compute changes without stamping would break because `_abilDoor` is missing (fallback to door A might miscount).  
- UI changes relying on `ownsAbility` require the helpers to be present first.  
The verification notes that "6 new fixtures pass" only with the full change, and disabling the guard causes 8/20 new checks to fail—indicating the parts are interdependent. Attempting to split would require maintaining multiple temporary flags or stubs, increasing surface area for error. The monolithic approach ensures atomicity: either all parts work together to enforce the guard, or the change is reverted. Given the small scope (only `engine.js` and `engine-data.js` modified per Files involved) and the tight coupling, splitting offers no safety advantage.  

**Finding:** The changes are intrinsically coupled; splitting would create fragile intermediate states without reducing risk.  
**Rank:** LOW (certainty: certain) – the verification’s dependency on the full set of changes confirms indivisibility.
