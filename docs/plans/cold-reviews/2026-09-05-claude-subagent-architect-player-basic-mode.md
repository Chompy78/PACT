## 1. Does this plan actually achieve its stated goal?

Mostly yes, on its own terms. The stated goal is a server-side-enforced one-active-character cap that can't be bypassed by calling the database directly. The trigger-based approach (step 2) does address that: a `BEFORE INSERT` trigger fires regardless of which client or credential performs the insert, so it's not merely a policy check that a clever client could route around by matching some other condition — it's a hard gate at the row level. Combined with the "exactly one insert code path" verified claim, the client-side catch (step 4) is a UX nicety layered on top of a real enforcement mechanism, not a substitute for it. That satisfies "not just a hidden button."

Where it's weaker than "achieves the goal" without qualification: the goal as stated is about restricting "a specific player's account," but the plan's own open question admits the authorization model for *who* can flip that flag is unresolved. A plan that ships the enforcement mechanism but defers the authorization decision hasn't fully achieved a feature whose entire premise is "someone with the right authority flags a player" — the authority part is exactly as central as the enforcement part, and it's the part left as a coin flip ("defaulting to (a) in this draft"). So: the *technical* gate is achieved; the *feature* as a coherent, defensible product decision is not yet fully specified.

## 2. Are any of the "Verified" claims suspicious?

A few are asserted with more confidence than the surrounding evidence supports:

- **"There is exactly ONE code path in the whole app where a genuinely new character row gets inserted."** This is a strong claim about the *entire* app's insert surface, based on tracing a shared function both editing tools call through. It doesn't account for: admin/scripted paths, a possible future import/duplicate feature, Supabase edge functions, or any batch/seed tooling that might insert rows directly rather than through the client library. The trigger itself doesn't depend on this claim (it fires on any INSERT regardless of caller — the plan says as much in step 2), so this is really only load-bearing for step 4 (the client-side friendly-error UX), not for correctness of enforcement. But it's phrased with total certainty ("exactly ONE," "there is no second... path to worry about") for something that's inherently hard to prove negative-space claims about just by reading code — it's the kind of claim that's true until someone adds a bulk-import button next quarter. Worth softening or at least flagging as "true as of this session's grep, re-check before relying on it in step 4."

- **The live-data row count** ("a few dozen rows... under a dozen distinct owners") is appropriately hedged as a snapshot, which is good practice — no issue there, just noting it as the one Verified claim that self-labels its own shelf life. The others don't.

- **The DB-driver detail** ("surfaces a raised exception's message but not a typed error code") is stated as fact but is the kind of infrastructure detail that's easy to get subtly wrong (many Postgres drivers *do* surface a SQLSTATE or error code alongside the message, even if this codebase's existing pattern chooses to match on message substring for other reasons, e.g. driver wrapping/logging behavior). If that premise is wrong, the plan's whole "distinctive substring" client-matching design (step 2 and step 4) is solving a problem that has a cleaner solution (match on error code instead of string substring, which is far less brittle against future message-wording changes). This is the single most consequential unverified technical assumption in the plan, and it's presented in the "Verified" bucket, not the "Assumed" bucket, which is arguably where it belongs given how much design weight rests on it.

- **"There is no 'admin' or 'superuser' role anywhere in the schema."** This is a clean, checkable negative claim (schema introspection), so it's more trustworthy than the code-path one, but it's worth noting the plan uses this absence to justify option (a) in the open question by elimination rather than by an actual argument for why "DM of a shared campaign" is the *right* authority — it's really just "the only thing that exists," not "the thing that should exist."

## 3. Is there a better alternative to the proposed approach that the plan didn't consider?

A few worth naming:

- **Match on Postgres error code (SQLSTATE) instead of a message substring**, if the driver does expose it (see above) — this is strictly more robust than string-matching and the plan doesn't evaluate it as an option, presumably because it inherited the existing locked-history trigger's pattern uncritically ("this codebase already has the exact pattern to copy" is treated as sufficient justification rather than re-examined). Copying an existing pattern is reasonable for consistency, but the plan's Alternatives section never actually considers *whether the existing pattern itself is optimal*, only whether to use a trigger at all vs. RLS-only vs. client-only.

- **Enforce via a constraint/partial unique index instead of a trigger.** A partial unique index (e.g., unique on `owner_id` where `archived_at IS NULL AND` some basic-mode marker) could enforce the one-active-character invariant more declaratively and would fail fast with a distinct, matchable constraint-violation error (constraint name), which is arguably a *more* reliable client-detection anchor than a raised message substring, and doesn't require executing a COUNT subquery inside a trigger on every insert. This wouldn't naturally handle the "only when basic_mode flag is set" conditionality as cleanly as a full unique index (partial indexes with subqueries referencing another table aren't straightforward in Postgres), so a trigger may still win, but the plan doesn't show it considered and rejected this option — it jumped straight to "copy the existing trigger pattern."

- **Doing the authority decision as a separate, prior decision record before any code plan.** Covered more under Q5, but worth flagging here as an "alternative approach" too: an alternative to *this* plan is a two-phase plan — phase 1 ships the schema column + trigger + client message-handling with the flag settable *only* via direct DB access (matching option (b) from the open question) as an interim state, and phase 2 adds the DM-facing authorization and UI once the authority question is actually resolved as a decision. This decouples the well-understood, low-risk enforcement mechanism from the genuinely undecided trust-boundary question, and would let the support pain point get addressed sooner without prematurely encoding a possibly-wrong authority model into a DM-facing UI that then has to be walked back.

## 4. What's missing?

**Edge cases / failure modes not addressed:**

- **Concurrent inserts / race condition.** Step 2's trigger counts existing non-archived rows and compares to the limit. If two inserts for the same flagged owner happen concurrently (e.g., a double-click, or two devices syncing near-simultaneously), a naive `COUNT() >= 1` check in a `BEFORE INSERT` trigger without additional locking can race — both transactions could see count=0 and both succeed, leaving two active characters even under the flag. The plan doesn't mention whether the trigger needs a row lock (`SELECT ... FOR UPDATE` on the owner's rows, or a serializable check) to close this gap. This is exactly the kind of edge case a security-advisor tool likely won't catch, since it's a logic race, not a permissions gap.

- **What happens to an *update* that un-archives a character** (sets `archived_at` back to null) for an already-at-or-over-limit flagged player? The plan's trigger is `BEFORE INSERT` only. If "un-archive" is implemented as an UPDATE (which seems likely, since the shared save function is described as "UPDATE first, INSERT only if zero rows affected"), then a flagged player at the limit could still un-archive a second character via UPDATE and bypass the intended cap entirely, since the trigger never fires. This is a real gap in the "Verified" architecture claim itself: the plan asserts the single insert path is what matters, but un-archiving is an update to an *existing* row, not a new INSERT, and the plan never addresses whether basic mode should also cover that case. This seems like a meaningful omission given how central "one code path" is to the design.

- **The DM-authorization function's own race/edge case**: what happens if the DM who flagged the player later leaves the shared campaign, or the campaign is deleted — does the flag persist with no one able to un-set it? The plan doesn't address flag "orphaning."

- **"Done when" checkability**: Most items are objectively checkable (refusal message appears, unflagged unaffected, toggle off unblocks, regression suite green, advisor clean). But "the change is documented per this project's own decision-record convention" is only checkable if that convention's format/location is itself well-defined elsewhere — the plan doesn't restate what that convention requires, so an external reviewer (or future implementer) can't verify this criterion from the plan text alone; it's a pointer to an external artifact, not a self-contained check. Similarly, "a DM sharing a campaign with a player can flag that player's account" bakes in the still-open authority-question answer as if it were already decided — if the open question resolves to option (b) instead (manual DB-only), this "Done when" criterion is simply wrong and needs rewriting. That's a structural issue: the Done-when list assumes a resolution to a question the plan itself says is unresolved.

- **No mention of what error the *policy* layer (not just the trigger) would show if the trigger is somehow skipped or interacts oddly with the policy** — e.g., does the existing INSERT policy's `WITH CHECK` need any modification, or does the plan rely purely on the trigger while leaving the policy untouched? The Alternatives section rejects "policy-only" but doesn't clarify whether the *existing* policy needs a compensating no-op confirmation that it won't conflict with the new trigger (e.g., firing order, or the policy passing before the trigger even runs and thus the trigger being the true last line of defense — that's probably fine but isn't explicitly confirmed).

## 5. Should this be split into more than one plan?

Yes, and the plan's own text makes the case for this better than I could. The "who can set the flag" question is explicitly called out as "the single biggest open question," and it is a genuine trust-boundary decision, not an implementation detail: it determines whether any DM can now reach across campaign boundaries to restrict a player they have no established relationship with (a real authority-scope-creep concern for a multi-campaign app), or whether the feature is deliberately hobbled to database-only for its initial cut. Baking a default answer ("defaulting to (a) in this draft") directly into a code plan — with UI, a DM-facing function, and a "Done when" line that assumes that answer — pre-commits an architecturally significant, hard-to-reverse trust decision (once DMs have a UI toggle and start using it on players, walking back the authority model is a product/support problem, not just a code revert) inside what's framed as mostly a schema-and-trigger plan.

The cleaner sequencing: resolve "who can flag a player" as its own short decision record first (it doesn't require any code exploration to decide — it's a policy question about the app's trust model), *then* write the implementation plan against that resolved answer. Alternatively, split as noted in Q3: ship the enforcement mechanism (schema column + trigger + client error handling) now, since that part is well-reasoned and low-ambiguity, and gate the DM-facing authorization UI (steps 3 and 5) behind the separate decision. That also shrinks the blast radius of the first shippable increment — enforcement-only, flag settable by hand, no new UI surface — while the harder question gets proper deliberation instead of a draft default.
