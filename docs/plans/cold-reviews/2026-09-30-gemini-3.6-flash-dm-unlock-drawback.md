# dm-unlock-drawback-review-claude-3-7-sonnet.md

**Model:** Claude 3.7 Sonnet (via Direct API Call, default settings)

## Overall Judgment

The document is well-written, logically structured, and highly detailed. It demonstrates strong operational discipline—particularly by requiring verification against the live database definition to prevent repeating the security guard regression documented in Fact 5. 

The scope is appropriately minimal, tightly constrained to adding an append-only `dmUnlockDrawback` event without altering AP accounting or introducing destructive backdoors. The logic of keying the unlock to a specific purchase event via `seq` is sound, as it avoids ambiguity when multiple drawbacks share the same name.

## Answers to Required Questions

### a. Does this achieve the goal without widening a DM's powers beyond unlocking?
**Yes.** 
- It adds a single event type (`dmUnlockDrawback`) to the RPC allowlist.
- It explicitly strips `cost` and `amount` attributes, ensuring no spendable AP is generated or deducted by the unlock itself.
- It enforces strict database-level checks requiring a matching `buy` event (`cat='drawback'`, `dmEdit: true`, `dmLocked: true`).
- DM actions remain strictly append-only; DMs cannot delete, alter existing event attributes, or forcibly remove the drawback. The player must still initiate and pay for the buyoff.

### b. Which assumptions (a)–(c) or verified-facts look shaky, and what would you check?
- **Assumption (a) (`seq` uniqueness):** **Shaky.** The plan assumes `seq` is unique within a character's `LOG`, but notes that imported logs might contain duplicate `seq` numbers. If an imported log has duplicate `seq` values, the database check (`exactly one event... with seq=targetSeq`) will fail, blocking legitimate unlocks for imported characters.
  * *What to check:* Query live character logs to verify if duplicate `seq` values currently exist in production data. Consider adding a check or fallback to handle legacy/imported duplicate `seq`s.
- **Assumption (c) (Old cached clients ignore unknown event types):** **Shaky / Unverified.** If a cached client encounters `{type: 'dmUnlockDrawback'}` during a sheet fold and its `switch` statement lacks a `default` case or throws on unknown types, the entire sheet view could crash for that user.
  * *What to check:* Audit `js/engine.js` (and any other event-iterating client code) to verify that unhandled `type` strings pass through safely without raising exceptions.
- **Fact 6 vs. Security Boundary:** Fact 6 states character owners can directly update their `stats` JSON column, meaning `dmLocked` is purely a UI/UX restriction today. The plan maintains this status quo, which is acceptable for UX, but calling it a "lock" could give DMs a false sense of security regarding player tampering.

### c. Is there a better alternative, especially to keying by `seq` or to the protected-projection change?
- **Keying by `seq`:** Keying by `targetSeq` combined with `refVal` is the cleanest option within an append-only JSON event array without migrating to full event UUIDs. The alternative—keying by `refVal` (drawback name)—was rightly rejected because FIFO matching breaks when a character has both an imposed and a player-purchased instance of the same drawback.
- **Protected projection change:** Adding `dmUnlockDrawback` to `pact_ap_ledger_protected` is correct. It ensures that once an unlock event is recorded, a player cannot strip the unlock event out of historical logs prior to a `sessionSeal`.

### d. What is missing — particularly any way this could move AP, be abused by a non-DM, or lose a guard?
1. **Unlocking already-bought-off or unlocked drawbacks:** The plan does not explicitly verify in the DB check whether the target drawback is *currently still open* (i.e., not already bought off). Allowing an unlock on an already bought-off drawback pollutes the event log.
2. **Campaign / Character boundary check:** The plan relies on existing RPC checks (`is_campaign_dm`). It must be verified that `dm_edit_character_log` explicitly validates that `p_character` belongs to a campaign where `auth.uid()` is currently designated as DM, preventing a DM of Campaign A from editing characters in Campaign B.
3. **AP leak check during buyoff:** While `dmUnlockDrawback` itself moves 0 AP, when the player subsequently calls `buyoffDrawback()`, the system must correctly evaluate `dmRemovalCost` (`flat` vs `expensive`). Ensure the buyoff logic correctly references the original buy event's `dmRemovalCost` when deducting AP.

### e. Specific Policy Decisions

- **Should `note` be required?** **Yes.** Requiring `note` (and validating `length > 0` and `<= 200`) enforces the stated business requirement that unlocking requires a recorded story beat.
- **Should unlock be one-way?** **Yes.** Making unlocks permanent and non-reversible keeps the event model simple and prevents DM/player state flip-flopping.
- **Should unlocking an already-bought-off drawback be rejected or ignored?** **It should be REJECTED.** The DB validation query should include a check that the target purchase event does not already have a corresponding `buyoff` event in the character's `LOG`.

### f. Should the lock become server-enforced now, or stay client-honoured (fact 6)?
**Stay client-honoured for this plan.** 
Server-enforcing the lock requires modifying the RLS policies/triggers that validate player writes to `stats`. Deferring this keeps the scope of `feat/dm-unlock-drawback` focused and low-risk. However, this decision should be explicitly documented in the plan's limitations.

### g. Is the Verification section objectively checkable? Should this split into more than one plan?
- **Checkability:** **Yes.** The verification items are concrete: inspecting `prosrc` string markers via SQL, asserting engine output in Node scripts, and running fixture tests.
- **Splitting:** **No.** The change is small and cohesive (1 new event type, 1 RPC modification, engine handling, and UI additions in DM Console/Live Sheet). Splitting it would add unnecessary overhead.

Approve the plan subject to adding a check in the DB validation logic to reject unlocks on already-bought-off drawbacks, and verifying Assumption (c) regarding old client event handling.
