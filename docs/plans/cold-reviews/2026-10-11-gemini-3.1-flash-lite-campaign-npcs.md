## Review
The document is exceptionally clear, well-scoped, and professionally structured. By choosing to leverage the existing `characters` table rather than creating a new entity, the author maintains the integrity of the "Live Sheet" and AP-awarding infrastructure while solving the primary friction point (one-per-campaign limitation) via a filtered unique index.

### Does this achieve the goal?
Yes. The plan successfully bypasses the "one-per-campaign" restriction for DMs while preserving it for players, and it effectively segregates NPC data from the player-centric features (ledger, bulk actions, basic mode) through logical filtering at both the SQL and client-side (DM Console) layers.

### Shaky assumptions
*   **The `is_dm_of_player` filter:** You assume that for the purpose of "basic mode," a DM should not be counted as a player. However, if a DM *is* also a player in their own campaign (an edge case, but possible), they might effectively bypass their own "basic mode" constraints by flagging their character as an NPC. The plan mentions a DM never needs an NPC to be a *player* character at the same time, which is a strong boundary, but it might be worth verifying if a "self-DM" can accidentally disable their own basic mode protections.
*   **"Declare downtime" impact:** You note that applying downtime to NPCs is harmless. While technically true that no player sees them, if an NPC is part of the "ledger" and "downtime" calculation, could a DM accidentally "lock" an NPC during a critical session, preventing its use? This seems minor but should be confirmed as a non-issue.

### Is there a better alternative?
No. The alternatives (new table or per-feature filtering) were correctly identified as inferior. Using the `is_npc` flag with a filtered unique index is the most idiomatic and "dry" way to handle this in a Postgres/Supabase environment.

### What is missing?
*   **The "Double-Dip" risk:** You mention the race guard is maintained by the `where` clause of the index, but ensure that `bind_character_to_campaign` (the player join) is explicitly updated to check `is_npc = false`. If the server-side code for a player join doesn't check the `is_npc` status, could a player potentially "hijack" a slot if a DM unbinds an NPC? (Though the `dm_bind_npc` ensures only DMs set the flag, this is a logic path that needs careful verification).
*   **Unbinding side effects:** You mention `dm_unbind_character` triggers the cleanup. If a DM is removed from a campaign, you stated: "remove_dm additionally unbinds the removed DM's NPCs". This is vital. Ensure that `remove_dm` handles the case where multiple NPCs exist (e.g., a loop or a set-based update).

### Is the verification objectively checkable?
Yes. The reliance on SQL-level tests (`sql-guards`) is the correct approach. Since you have provided the list of specific SQL tests to run (e.g., "DM binds two NPCs," "player refused second join"), this is objectively verifiable.

### Should this split into several plans?
No. The change is small enough that splitting it would likely lead to "integration hell" between the SQL schema changes and the DM Console UI updates. Keeping them together allows for a single, coherent migration and deployment.

### Overall Verdict
The plan is robust. The most critical risk is a leaked `is_npc` row into a player-facing `limit 1` or `count` query. The proposed strategy of adding `and not is_npc` to all those functions is the correct mitigation. The logic holds up against cold review.
