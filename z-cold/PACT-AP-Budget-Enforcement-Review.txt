PACT AP-BUDGET ENFORCEMENT REVIEW
================================

Context
-------
PACT deliberately uses a single source of truth for rules/pricing:

  js/engine.js

The project explicitly rejects duplicate pricing logic in SQL, triggers,
policies, or a second JS implementation.

Current situation:
- Character LOG is client-writable.
- Frozen event costs are client-writable.
- Entire character stats blob is client-writable.
- DM AP (characters.ap) is the only truly server-authoritative value.
- Current shipped enforcement is primarily a client-side save gate.

Core Conclusion
---------------
Without some server-authoritative execution of the rules engine,
the server cannot prove that a character is legitimately within budget.

It can only prove that the submitted data is internally consistent.

In other words:

  "within budget"
  !=
  "claims to be within budget"

Server-Side Options
-------------------

1. Full SQL pricing reimplementation
   Status: Rejected

   Reason:
   - Violates single-source-of-truth rule.
   - High drift risk.
   - Creates permanent maintenance burden.

2. Narrow frozen-cost integrity checks
   Status: Viable

   Example:
   - Sum frozen event costs.
   - Validate stored totals.
   - Validate inexpensive structural invariants.

   Benefits:
   - Catches corruption.
   - Catches buggy clients.
   - Catches malformed imports.
   - Catches accidental inconsistencies.

   Limitation:
   - Does NOT prove costs are correct.
   - Attacker can submit self-consistent fake costs.

   Conclusion:
   - Useful integrity layer.
   - Not true anti-cheat protection.

3. Supabase Edge Function running engine.js
   Status: Strongest option (if project rules allow it)

   Concept:

      Browser
           |
           | LOG
           v
      Edge Function
           |
           | import engine.js
           | compute()
           | validate budget
           v
      database write

   Benefits:
   - One pricing implementation.
   - No SQL duplication.
   - Real server-side enforcement.
   - Eliminates trust in client-submitted costs.

   Cost:
   - Requires server-side execution of engine.js.
   - Whether this counts as "backend" is a project-policy question.

Threat Model Observation
------------------------
The most realistic attacker is probably not a programmer.

The most realistic attacker is:

  player + AI assistant

A modern AI can:
- Inspect exported JSON.
- Find AP-related values.
- Reduce frozen costs.
- Rewrite logs.
- Produce internally consistent payloads.

The AI does NOT need to understand PACT rules.

Therefore:

  "AI won't help users cheat"

is not a viable defence model.

Even if frontier assistants refuse, local/open-weight models exist.

Conclusion:
- Do not rely on AI refusal.
- Assume attackers can obtain AI assistance.

CharGen Review
--------------

Recommendation:
Keep draft mode permissive.

Reason:
CharGen's purpose is exploration.

Useful workflow:

  Draft:
    - allow overspend
    - show warnings
    - show deficit

  Lock:
    - refuse if over budget

  Cloud Save:
    - refuse if campaign enforcement enabled

This preserves experimentation without weakening enforcement boundaries.

Implementation Preference
-------------------------
Prefer one invariant check rather than duplicating logic across handlers.

Preferred pattern:

   mutate()
   recompute()
   validateBudget()
   refreshUI()

Avoid embedding budget logic independently into every delegation path.

Visibility Helps
----------------
Consider making integrity state visible to DMs.

Examples:

  Cloud-valid: YES

  Integrity warning: detected

  Failed consistency check

Visibility often deters abuse without adding large amounts of complexity.

Recommended Next Step
---------------------

If project policy forbids any server execution of engine.js:

  Recommendation:
    Keep current UI enforcement and add narrow DB integrity checks.

If project policy allows Supabase Edge Functions:

  Recommendation:
    Run the existing engine.js inside an Edge Function and validate
    budget server-side before accepting writes.

Final Position
--------------
The current client-side enforcement is likely sufficient for the vast
majority of honest users.

The only way to obtain genuine server-side proof that a build is within
budget while preserving a single source of truth is to have the server
execute the same engine.js used by the client.

Anything else can improve consistency and error detection, but cannot
establish trust in client-authored frozen costs.

Additional Note
---------------
Decide explicitly which threat is being defended against:

1. Honest mistakes and normal UI use.
2. AI-assisted player editing JSON.
3. Determined malicious client.

The chosen threat model should drive the architecture more than the
implementation details.
