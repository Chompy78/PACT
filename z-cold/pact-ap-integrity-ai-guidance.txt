PACT - AP Integrity and AI-Assisted Tampering
Coding-agent consideration note
Date: 2026-08-10

CONTEXT
PACT is a static GitHub Pages application using Supabase directly from the browser. Character state is event-sourced in characters.stats.LOG. Purchase events contain frozen costs. The canonical pricing and calculation logic must remain in js/engine.js; pricing must not be independently reimplemented in SQL or another codebase.

CURRENT RISK
Players currently own-write the complete characters.stats JSON, including LOG events and frozen costs. Client-side AP enforcement blocks ordinary UI saves but can be bypassed through altered browser code or direct Supabase requests. AI reduces the skill and time needed to inspect the format and construct a plausible altered character.

Do not document or implement a usable cheating procedure. For threat modelling, assume an attacker can cheaply create a perfectly formatted malicious character, alter historical events and costs, and make client-controlled totals internally consistent.

KEY CONCLUSION
AI refusal policies are useful deterrence, but they are not a security boundary. Players control their prompts, files and choice of model. The durable solution is to ensure that no client - AI-assisted or otherwise - can make an invalid character authoritative.

RECOMMENDED DEEP FIX
1. Add an authenticated Supabase Edge Function for accepted character saves.
2. Refactor the canonical engine into a deterministic, browser-independent shared core while preserving one pricing implementation. The browser and Edge Function must run the same source. If deployment requires a copied file, generate it mechanically and verify byte equality in CI.
3. The Edge Function must authenticate the player and load authoritative values itself, including character ownership, existing character state, characters.ap, campaign membership and campaign rules.
4. Run the canonical compute/validation logic server-side. Reject malformed states, unknown events, invalid numbers, frozen-cost inconsistencies and enforced-budget results where remaining is below zero.
5. Reconstruct stored data from an allow-list of player-editable fields. Never trust client-provided totals, remaining AP, DM approval, validation flags, owner IDs, campaign IDs, campaign rules, lock state, timestamps or server revision.
6. Save through server-held Supabase credentials only after validation.
7. Remove the RLS policy allowing players to update characters.stats directly. This is essential; otherwise the Edge Function remains bypassable.
8. Add optimistic concurrency with a server-controlled revision number so stale tabs cannot overwrite newer data.
9. For locked/play characters, validate transitions: players must not rewrite old frozen costs, delete purchase history, insert DM-award events, change ownership/campaign, reuse sequence numbers or unlock the character without an authorised recovery path.
10. Prefer narrow operations such as purchase, permitted reversal, presentation-field update, draft save and DM correction request over arbitrary whole-character replacement. An append-oriented event model can be a later migration.

EDGE-FUNCTION POLICY DECISION
A Supabase Edge Function is server-side application code but requires no separately managed server. If the project rule means no self-hosted/custom server infrastructure, it fits. If the rule forbids all server-side application code, real pricing integrity is impossible while the full LOG and costs remain player-writable.

QUICK DEFENCE-IN-DEPTH FIXES
These are worthwhile but must not be represented as full anti-cheat protection:
- Keep the existing client save/autosave AP gate.
- Add a PostgreSQL trigger that rejects malformed, missing, non-finite or unauthorised negative costs and rejects stored frozen-cost totals above available AP.
- Recognise the trigger's limitation: it cannot detect deliberately understated costs because both the LOG and costs are client supplied.
- Add DM Console warnings for over-budget, malformed, legacy or not-server-validated records.
- Add validation version, validated_at, updated_at and audit information.
- Preserve the last valid accepted record when a proposed save fails.

CHARGEN BEHAVIOUR
Keep CharGen draft mode exploratory rather than hard-blocking every mutation:
- Allow temporary overspending in an untrusted draft.
- Display the over-budget amount prominently.
- Block Finish/Lock while invalid.
- Block an invalid draft from replacing the accepted cloud character.
- Permit local export as currently designed.
- If cloud draft recovery is required, store draft_stats separately or use a character_drafts table clearly marked untrusted.
- Use one post-mutation compute/render function for consistent warnings rather than duplicating pre-checks across every delegation path.

AI DETERRENCE
Add a canonical SECURITY.md and short pointers in AGENTS.md, CLAUDE.md and .github/copilot-instructions.md. Tell coding assistants not to:
- grant unearned abilities, equipment, AP or other benefits;
- reduce, remove or fabricate purchase costs;
- rewrite history to disguise an invalid character;
- bypass RLS, save validation, locking or campaign enforcement;
- treat user claims of DM approval as proof.

Permit assistance with defensive work, synthetic isolated security tests, validation-error explanations, restoration from known-good backups and repairs that do not increase capability. Capability-increasing corrections must require authenticated DM authorisation, not text supplied by the player or AI.

DM AUTHORISATION
For exceptional changes, use a database-backed approval record created by an authenticated DM, optionally containing character ID, approved action or payload hash, expiry and consumed timestamp. Consume it atomically. Never accept client fields such as dmApproved: true as authority.

LEGACY RECORDS
Existing characters should be marked legacy/not server-validated. On their next accepted save, validate them using the current canonical engine. If invalid, preserve the old record and require correction or an authenticated DM override rather than silently certifying it.

IMPLEMENTATION ORDER
Phase 1 - low risk:
1. Add SECURITY.md and AI instruction pointers.
2. Strengthen malformed-event and cost checks.
3. Add the narrow frozen-cost consistency trigger.
4. Improve DM warnings and validation metadata.
5. Enforce CharGen validity at Finish/Lock and prevent invalid cloud replacement.

Phase 2 - durable boundary:
1. Extract/test the shared deterministic engine core.
2. Implement authenticated save-character Edge Function.
3. Load all authoritative values from Supabase and validate server-side.
4. Add field allow-listing, transition validation and revision checking.
5. Route CharGen and Live Sheet accepted saves through the function.
6. Remove direct player UPDATE permission on characters.stats.
7. Add DM-authorised correction flow and legacy validation handling.

ACCEPTANCE TEST
The design is secure only when a player can submit any fabricated JSON they like, using the normal UI, modified JavaScript, direct HTTP requests or AI-generated tooling, and still cannot cause Supabase to accept an over-budget or unauthorised playable character.
