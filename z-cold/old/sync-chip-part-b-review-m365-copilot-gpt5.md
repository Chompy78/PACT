# Cold review: Shared cloud-sync status chip + universal autosave (Part B)

**Review posture:** cold review based only on the supplied plan; no codebase access and no code-correctness claims.

## Overall judgement

The three-branch structure is materially better than a single-pass implementation, and the plan genuinely addresses several previously vague areas. However, I would not implement it unchanged. Two conceptual gaps undermine the central promise of a shared, **honest** status chip:

- the six-state vocabulary cannot represent a signed-in character that is intentionally local-only and not eligible for cloud autosave; and
- `pendingEdit` is proposed as a Boolean even though edits can occur while a save is in flight, creating a race that can falsely clear unsaved work.

The freshness design also cannot guarantee that an `idle` chip remains truthful while a tab stays active. This is acceptable only if the UI explicitly communicates that freshness is sampled rather than continuously known, or if another refresh trigger is added.

## Findings

1. **`blocking`, `high` — The state vocabulary has no honest state for “signed in, but this character is intentionally local-only/not cloud-enrolled”.** Under B3, a never-manually-cloud-saved character must remain local-only after sign-in. Under B1/B2, an edit immediately sets `pendingEdit`, which is treated as cloud `dirty`; alternatively, if such edits are excluded, the chip can show `idle`, which implies cloud synchronisation despite no cloud row or consent. Either result conflicts with the “shared, honest cloud-sync status” goal. **Suggested improvement:** define the chip’s subject and add an explicit `localOnly`/`notEnabled` state, or make the signed-in idle label unambiguously say that cloud saving is not enabled for this character. If the six-state vocabulary is immutable, document how signed-in local-only characters are represented without falsely implying either a pending save or an up-to-date cloud copy.

2. **`blocking`, `high` — A Boolean `pendingEdit` is insufficient to prevent an edit-during-save race.** Sequence: edit A schedules/pushes; while A is in flight, edit B sets `pendingEdit=true`; A succeeds and reports `dirty:false`; the proposed clear rule can clear B even though B has not been pushed. The chip may briefly or indefinitely report `idle` while real unsaved edits remain. The same race affects “successful push means no longer behind” if the successful push did not include the latest local revision. **Suggested improvement:** use a monotonically increasing local edit generation/revision. Capture the generation included in each push and clear pending state only when the acknowledged generation equals the current generation and no later debounce/in-flight operation exists. State transitions need explicit race tests.

3. **`blocking`, `high` — Ownership and transport of `pendingEdit`, `saving`, and `behind` are not designed sufficiently for a shared `getSyncState(id)`.** The plan says each tool owns a local flag, while `getSyncState()` lives in `js/sync.js`, but it does not define how the module observes tool-local state, whether state is per-character, whether it survives character switches, or how UI code is notified of transitions. Polling `getSyncState()` only during render would miss asynchronous save/freshness completion; a singleton Boolean could leak state between characters. **Suggested improvement:** specify a per-character state record and a small API such as `markPendingEdit(id, generation)`, `subscribeSyncState(id, callback)`, and operation start/finish transitions. Define cleanup on character switch, sign-out, failed auth, and page teardown.

4. **`blocking`, `high` — Focus/visibility checks do not make an always-visible `idle` status honest.** If the tab remains focused while another device changes the character, `behind` is never discovered. The chip can continue to say idle indefinitely. The plan openly defers realtime and polling, but that limitation is load-bearing because the stated goal is an honest cloud status indicator, not merely “status as of the last focus event”. **Suggested improvement:** either add bounded idle polling, or change the semantics/UI to disclose sampled freshness—for example, “Up to date as of 11:05” with an explicit refresh action. At minimum, run freshness checks on relevant character selection/load and immediately before presenting `idle` after long elapsed time. Document the maximum staleness guarantee.

5. **`moderate`, `high` — The six states omit offline, failed-save, unauthorised/expired-session, and unknown-freshness conditions.** A failed push may remain `dirty`, but “dirty” does not tell the user whether autosave is merely pending, blocked by offline status, rejected by auth, or repeatedly failing. A chip labelled “Saving” can also become stuck if every error path does not terminate the operation state. This weakens the word “honest”, especially for the plan’s own offline and expired-auth matrix. **Suggested improvement:** define how every failure maps to the approved vocabulary and provide adjacent actionable error text where a seventh/eighth chip state is prohibited. Add a timeout/finally rule for `saving`, and specify that auth expiry transitions the chip and suppresses retries until session recovery.

6. **`blocking`, `high` — The B3 consent rule and the retained `campaignBound` gate are not reconciled.** The proposal says manual cloud save is the one-time consent moment, but B3 still autosaves when `campaignBound || cloudEligible`. If a campaign-bound character can exist without a prior manual cloud-save consent event, campaign binding bypasses the proposed rule. If campaign binding already necessarily creates/confirms the cloud row, that dependency is not established in this cold-review text. **Suggested improvement:** state one authoritative eligibility predicate and prove how campaign-bound characters satisfy it. If campaign binding is a separate consent pathway, name and document it explicitly; otherwise use `cloudEligible` alone.

7. **`blocking`, `high` — “Confirmed cloud row derivable from the existing local cache” is not yet an objective eligibility definition.** Cache metadata can become stale, a server row may be deleted, a row may have been adopted rather than manually saved, or a local record may outlive sign-out/account changes. The proposed rule mixes two different concepts: server existence and user consent. Existing cloud-row knowledge may prove existence, but it does not necessarily prove that this user performed the intended one-time consent action. **Suggested improvement:** define the exact cache fields and invariants that establish eligibility, bind them to the authenticated user/account, and specify behaviour for missing/deleted rows. If the cache cannot distinguish manual enrolment from other cloud-row discovery, store an explicit local consent/enrolment marker—no schema change is required if only local persistence is needed.

8. **`moderate`, `high` — `behind` persistence and boot semantics remain unclear.** B1 says `checkFreshness()` sets/clears `behind`, but not where. In-memory-only state disappears on reload; persisted state may become stale across account changes or server-row deletion. The existing `reconcile()` reports `behind` transiently, so the plan needs to say how its result feeds the new state machine and whether a boot-time conflict is retained until resolved. **Suggested improvement:** specify storage location, account/character scoping, hydration, expiry, and clearing on sign-out or character deletion. Include a reload test in each state.

9. **`moderate`, `high` — `checkFreshness()` lacks defined semantics for important responses.** Comparing `updated_at` to `base_updated_at` does not cover no local base, missing remote row, duplicate/equal timestamps, malformed data, network failure, RLS denial, or auth expiry. “Unchanged” must not accidentally mean “request failed” and clear `behind`. **Suggested improvement:** define a result algebra such as `unchanged`, `remoteNewer`, `remoteMissing`, `unknown/error`, and only clear `behind` on a successful, authoritative unchanged comparison. State whether timestamps are treated as opaque equality tokens rather than ordered client-clock values.

10. **`moderate`, `high` — The precedence rule `saving > conflict` can temporarily hide the most important actionable state.** If a stale push begins before freshness information arrives, or a conflict is detected while an operation flag remains set, the user sees “Saving” instead of “Resolve conflict”. This may be harmless for milliseconds, but becomes misleading if refusal/error cleanup is imperfect. **Suggested improvement:** justify the precedence with transition invariants and a maximum duration, or prefer `conflict` over `saving` once conflict is known. Add a test where the stale-save guard refuses an in-flight save and confirm the final state and action.

11. **`moderate`, `high` — The conflict action is described as reuse of `loadCharacter(id, {onBehind})`, but the exact non-destructive UX contract is incomplete.** Reloading the cloud copy discards local edits. The plan mentions already-shipped backup features but does not state whether resolution automatically preserves/export the local version, what Cancel does, or whether repeated invocation remains possible. **Suggested improvement:** specify the confirmation text, preservation path, cancellation state, and post-reload transition. Verify that Cancel leaves `conflict` visible and actionable, and that accepting produces a recoverable local backup before replacement.

12. **`blocking`, `high` — B1 and B2 can expose a state machine before B3 defines eligibility, making branch independence questionable.** The branches are called independently mergeable, but B2’s truthful rendering depends on knowing whether the current character participates in cloud sync—an issue deferred to gated B3. Shipping B2 first risks a misleading chip for local-only characters. **Suggested improvement:** move the eligibility/readiness concept into B1 even if autosave remains off until B3, or merge B2 and the eligibility representation behind a feature flag. “Sequentially mergeable” would be more accurate than “independently mergeable”.

13. **`moderate`, `high` — DM Console treatment is sensible, but it conflicts with the headline claim of one six-state indicator across all three tools.** The narrower signed-in/out-only chip is probably the correct design, yet the Goal and Standing Scope still say one shared six-state vocabulary across all three. A future reviewer or implementer could reasonably treat the DM exception as non-compliance. **Suggested improvement:** revise the goal to “one shared visual/status language, with editor tools using six sync states and DM Console using the signed-in/out subset”. Define what signed-in identity/campaign information currently shown by `campWho` must be retained when replacing its signed-in portion.

14. **`moderate`, `high` — DM Console verification is not sufficiently objective for all three write paths.** “Verify/adjust existing per-action status elements” and “appropriate feedback” do not define success, failure, retry, duration, accessibility, or simultaneous operations. `award-status` may cover only one path. **Suggested improvement:** inventory each operation and require per-action pending/success/error feedback, no global cross-talk, accessible announcement behaviour, and reset rules. Test rejection and expired-auth cases for each path, not only presence of an element.

15. **`moderate`, `high` — The escaping requirement is correct but the proposed shared mapping does not itself solve dynamic-string safety.** A pure mapping of fixed icons/labels has no character or campaign names to escape. The risk reappears when each tool composes a fixed status with a dynamic name into `innerHTML`, `title`, or `aria-label`. HTML text escaping and attribute escaping also need a proven common contract. **Suggested improvement:** prohibit the shared mapper from accepting raw dynamic names, or have it return plain data that tool-local code assigns through `textContent`/DOM properties. Where `innerHTML` is unavoidable, add fixtures containing quotes, angle brackets, ampersands, and event-handler-like strings for every dynamic surface.

16. **`moderate`, `high` — Verification relies too heavily on an unrelated engine-parity test and manual exercises.** Keeping engine parity at zero is good regression coverage, but it cannot validate the new orchestration. “Exercise known cache states” is not a repeatable acceptance test, and the critical race conditions are unlikely to be found reliably by hand. **Suggested improvement:** add a small deterministic sync-state test harness with mocked auth, cache, server metadata, deferred promises, and controllable time. Cover precedence, edit-during-save, character switching, throttle boundaries, failed freshness calls, server deletion, auth expiry, and conflict cancellation/acceptance.

17. **`moderate`, `high` — The 30-second throttle is underspecified and may suppress the very check the trigger is intended to perform.** `visibilitychange` and `focus` often fire together; a shared throttle is sensible, but the plan does not define leading/trailing behaviour, whether a failed request consumes the interval, whether throttling is per-character, or whether switching characters bypasses it. **Suggested improvement:** make it per-character, leading-edge, single-flight, and do not treat an auth/network failure as a successful freshness sample. Character selection/load should force a check regardless of the previous character’s timer.

18. **`moderate`, `high` — Write-volume “re-measure before merging” has no acceptance threshold or measurement method.** Without a budget, the result cannot gate a merge. Debounce duration alone does not bound writes during continuous editing, retries, two open tools, or character switching. **Suggested improvement:** define representative edit traces, expected writes per active user/hour, retry behaviour, and an explicit acceptable Supabase quota margin. Instrument or count actual save attempts and successful writes separately.

19. **`minor`, `high` — Terminology is internally inconsistent.** The user-facing vocabulary says `signed-out`, `signed-in-idle`, and `dirty+behind`, while the state API returns `signedOut`, `idle`, and `conflict`. That can work, but “conflict” is both an internal state and a user-facing concept, and `behind` can mean clean-behind while `conflict` means dirty-behind. **Suggested improvement:** include one canonical state table defining internal key, prerequisites, visible label, action, entry conditions, and exit conditions.

20. **`minor`, `high` — The two-browser verification wording is ambiguous relative to the multi-tab exclusion.** “A two-browser-tab check” could mean two tabs in one browser, which shares local storage and tests part of the explicitly deferred same-browser coordination problem, or one tab in each of two browsers, which better simulates independent devices. **Suggested improvement:** specify both environments and expected limitations. Do not let the cross-browser test accidentally pass because both tabs share the same cache.

## Prior blocking findings: closure assessment

- **State machine — not fully closed.** The state names and precedence are proposed, but ownership, per-character scoping, notification, operation races, error mapping, and local-only eligibility remain unspecified. This is more than a restatement, but not implementation-ready.
- **Behind clear conditions — partially closed.** Three clear paths are named, which is useful. The successful-push rule is unsafe without edit generations, and failed/unknown freshness responses need an explicit “do not clear” rule.
- **Refresh trigger — partially closed.** Focus/visibility plus throttling is a concrete trigger, so the prior vagueness is resolved. It does not, however, support an unqualified continuously honest `idle` state while the tab remains active.
- **Conflict-resolution UX — substantially closed, with a moderate residual gap.** Reusing `onBehind` and avoiding “Force sync now” addresses the earlier dead-end. Local-edit preservation, Cancel behaviour, and post-resolution transitions still need acceptance criteria.
- **DM Console scope — substantially closed.** Restricting DM Console to shared auth visuals and operation-local write feedback is logically appropriate. The plan should align its headline scope with that exception and make the three action-status requirements testable.

## Sections that are solid

- Separating read-only freshness detection from mutating reconciliation is a sound design boundary.
- Reusing the existing conflict primitive rather than weakening the stale-save guard is the right structural choice.
- Explicitly excluding rules-engine and dataset-version changes is clear and appropriately scoped.
- Splitting implementation into state/orchestration, UI, and autosave-consent work is directionally correct, once eligibility is moved early enough to keep B2 truthful.

## Recommended disposition before implementation

Resolve Findings 1, 2, 3, 4, 6, 7, and 12 in the plan before starting B1/B2. The deepest fix is to define a per-character sync participation model and revisioned state machine first; that simultaneously resolves the local-only representation, pending-edit race, state ownership, and branch-dependency problems. The shallower alternative—patching labels and retaining Boolean flags—would be quicker but would preserve the exact class of misleading status the project is trying to remove.
