# Header Simplification + Universal Cloud Autosave — Cold Review

## Findings

- **blocking, high confidence — The plan has not defined the sync state machine well enough to guarantee that the six chip states are mutually meaningful.** `signed-in`, `saving`, `dirty`, `behind`, and `dirty+behind` can overlap in time, and the plan does not specify precedence, transition rules, or what happens on push failure, offline mode, auth expiry, load, character switching, or successful conflict resolution. In particular, `dirty` is described as “edited but not yet pushed”, while `saving` is an in-flight operation; the UI needs an explicit precedence model rather than six loosely described labels. **Suggested improvement:** define the state machine before implementation, including precedence (for example: signed-out → signed-in; saving supersedes dirty; dirty+behind supersedes either individual state; behind clears only after an explicit resolution; failures/offline get an explicit policy), and specify the exact transition for every sync outcome.

- **blocking, high confidence — “behind” is not safely equivalent to a persisted boolean on the cached record.** The plan says to persist `behind` after `reconcile()` discovers it, but it does not define when that flag is cleared or how it relates to the server version being observed. A stale boolean can survive after the user loads a newer server version, successfully force-syncs, switches characters, signs out, or otherwise changes the relevant baseline. **Suggested improvement:** persist the server revision/timestamp that established the behind state, define the baseline it is behind, and specify the authoritative transitions that clear it. Prefer deriving `behind` from a known server revision where practical rather than treating it as an independent fact.

- **blocking, high confidence — The proposed “force sync now” fallback is underspecified for the exact failure mode the plan is trying to protect against.** If autosave is broken, unavailable, offline, or has a failed request, the chip must remain actionable and the user must understand whether clicking it retries, overwrites, reconciles, or merely pushes the current local state. This is especially important for the existing stale-cloud-save guard: a force action cannot silently bypass conflict protection. **Suggested improvement:** define the force-sync contract explicitly: retry semantics, conflict behaviour, offline behaviour, success/failure feedback, and whether it can ever overwrite a newer server version. Keep conflict resolution distinct from “force” if necessary.

- **blocking, high confidence — Universal autosave changes the data-consent/default-behaviour model, but the plan leaves the user-facing migration decision open.** The plan correctly recognises that this is a behaviour change: merely being signed in now causes edits to reach the cloud. That is materially different from the current explicit-save model. Treating it only as a reviewer question risks implementing a surprising privacy/ownership change without a defined user experience. **Suggested improvement:** decide explicitly whether signing in constitutes consent to autosave. If yes, provide a concise first-use/status-chip explanation and document it in the UI/decisions log; if no, introduce an explicit opt-in or setting. Also define what happens to characters previously treated as local-only when a user signs in.

- **moderate, high confidence — The write-volume analysis is incomplete.** The plan identifies the free-tier/autopause risk but does not quantify or bound the new write load. Removing the campaign-bound gate could increase writes substantially, particularly if multiple editor tabs are open or users make frequent edits. The same debounce interval does not by itself guarantee an acceptable request rate. **Suggested improvement:** establish an expected maximum/minimum write cadence, coalescing behaviour, retry/backoff policy, and a rough upper-bound request model before implementation. If telemetry is unavailable, at least document a conservative estimate and a post-release monitoring threshold.

- **moderate, high confidence — Multiple open tabs/devices create race scenarios that are not fully specified.** Universal autosave plus polling can cause two tabs to alternate writes, repeatedly detect “behind”, or continually conflict. The plan relies on the existing stale-save guard but does not describe the user experience when both tabs are actively edited. **Suggested improvement:** explicitly define multi-tab behaviour, including whether a successful push from one tab clears another tab's dirty state, whether polling is allowed to overwrite local state, and how repeated conflicts are surfaced. Consider using a per-record revision/etag as the central concurrency primitive.

- **moderate, high confidence — “Reconcile on an interval and/or focus” is too open-ended for an implementation plan.** This is load-bearing for the new `behind` state, yet the key mechanism is left undecided. Without a concrete trigger/cadence, “newer-on-cloud” cannot be considered a complete feature. **Suggested improvement:** choose a bounded policy before implementation, such as visibility/focus reconciliation plus a conservative minimum interval while visible. State the intended maximum detection latency and request budget. If polling is deliberately deferred, remove “behind while idle” from the immediate goal rather than shipping an indeterminate implementation.

- **moderate, high confidence — The pagehide flush may not provide a reliable network-delivery guarantee.** The plan correctly identifies the lost-timer bug, but “flush on pagehide” is not equivalent to “the cloud write definitely reaches Supabase before the page disappears”. Normal async requests can be terminated during page dismissal. The cross-tool navigation case is stronger because it can await a promise before changing location, but ordinary tab close/discard remains inherently best-effort. **Suggested improvement:** distinguish “flush before deliberate in-app navigation” from “best-effort flush during page lifecycle termination”. For pagehide, use an appropriate transport/pattern if supported by the existing sync layer, or explicitly state that browser-close persistence is best effort. Add a verification case for both behaviours rather than claiming generic navigation safety.

- **moderate, high confidence — The plan conflates “save timer flushing” with the broader dirty-state invariant.** A pending debounce timer is only one representation of unsynced state. If a push is in flight, fails, is rejected as a conflict, or is superseded by another edit, simply clearing the timer does not establish that the cloud is current. **Suggested improvement:** make dirty state derive from a clear local-versus-server sync baseline, with explicit states for scheduled, in-flight, failed, and conflicted where necessary. A successful request should only clear dirty when the response confirms the server version corresponding to the local snapshot.

- **moderate, high confidence — Character identity/lifecycle transitions need explicit handling.** The plan adds autosave to standalone tools and moves sync state into shared storage, but it does not specify what happens when a user loads another character while a save is pending, creates a new character, signs out, or switches between local and cloud-backed records. A timer must never flush character A's state into character B's identity or leave the chip describing the wrong record. **Suggested improvement:** make every pending save keyed to an immutable character ID and snapshot/version; cancel or await obsolete work when changing records; define chip reset semantics on load/create/sign-out.

- **moderate, high confidence — DM Console's “shared chip” requirement is only visual, not actually shared.** Because the architecture duplicates markup/CSS/logic in three standalone files, the plan should be explicit that there is a canonical contract rather than merely saying “same structure”. Otherwise the three implementations will drift immediately. **Suggested improvement:** define a tiny shared vocabulary/spec (state names, ARIA label rules, icon/text mapping, CSS class names and precedence) in a project convention or shared module if architecture permits. If duplication is mandatory, add a verification check that the three copies remain identical in the relevant contract.

- **moderate, high confidence — Accessibility is missing from verification.** A status chip that changes from signed-in → saving → dirty → behind is dynamic status information and potentially an interactive control. Visual light/dark checks are not enough. **Suggested improvement:** specify keyboard accessibility, focus behaviour, accessible name/role, live-region behaviour for meaningful transitions, and non-colour-only state communication. Verify at least keyboard operation and screen-reader-visible state text.

- **moderate, high confidence — Error/offline states are conspicuously absent from the six-state vocabulary.** Real autosave systems fail: expired sessions, network outages, Supabase errors, quota/rate limiting, and RLS failures are all possible. Mapping all failures into “dirty” may be misleading because the user cannot tell whether a save is pending or repeatedly failing. **Suggested improvement:** either add an explicit `error/offline` state or define a precise rule that dirty/behind remains visible with a secondary failure indication and retry affordance. Do not let the UI imply that “saving” means success is imminent when the system is offline.

- **minor, high confidence — The verification matrix is too narrow around autosave success.** It tests two-browser dirty/behind states and the old three-second navigation loss, but not failed saves, offline/reconnect, auth expiry, character switching during a save, conflict resolution, or repeated edits while a save is in flight. **Suggested improvement:** add a small state-transition matrix covering success, failure, conflict, reconnect, navigation, and character switching.

- **minor, moderate confidence — “same chip markup” is an objective requirement but is not directly verified.** The current visual check could pass while the DOM structure, ARIA attributes, labels, or state semantics differ between files. **Suggested improvement:** add a source-level or fixture-based check for the shared chip contract, especially because there is deliberately no shared UI component.

## What looks solid

- The confirmed lost-debounce-on-navigation defect is a legitimate and well-scoped reason to fix the existing autosave mechanism before generalising it. The plan also correctly separates that confirmed defect from the owner's earlier report rather than falsely claiming causation.
- The decision to replace rather than add another header indicator is coherent with the stated simplification goal.
- Keeping the existing stale-write/concurrency guard is important; universal autosave should not become an excuse to weaken conflict protection.
- Keeping debounce rather than pushing on every keystroke is sensible, provided the final design defines failure, in-flight, and flush semantics.
- The plan appropriately keeps rules-engine changes out of scope and recognises that the rules regression suite should remain at zero failures.
- Folding the already-planned sign-in-indicator task into this change avoids duplicated UI work.

## Alternatives / structural recommendation

The strongest alternative is not to abandon universal autosave, but to make `js/sync.js` the authoritative sync state machine rather than adding more orchestration separately inside each HTML file. The standalone pages can still duplicate the small presentation layer, but they should consume a common, well-defined sync contract. That would reduce the risk that CharGen and Live Sheet implement subtly different dirty/behind/conflict behaviour.

I would also avoid making “persist a `behind` boolean” the core abstraction. A server revision/base timestamp plus local revision is a stronger model: the UI can derive whether the current local snapshot is ahead, equal, or behind the known server baseline, while conflict handling remains tied to the existing concurrency guard.

## Overall assessment

The plan has a strong goal and correctly identifies a real autosave defect, but I would **not implement it unchanged**. The biggest risks are not the chip styling or the debounce itself; they are the undefined sync state machine, unclear lifecycle/concurrency semantics, and the unmade decision about what universal autosave means for user expectations and cloud-data behaviour.

The plan becomes substantially safer if implementation starts by specifying the sync-state contract and character lifecycle/concurrency rules, then fixes the navigation flush, then generalises autosave, and only then builds the shared presentation layer.
