# Review: Charge species/heritage packs as real purchases

**Overall verdict:** Do not implement this plan unchanged. The goal is reasonable, but the proposed mechanism does not simultaneously guarantee (1) the sum invariant, (2) meaningful per-line pack and trait prices, and (3) frozen historical pricing. Several steps rely on those properties being compatible when a later event changes pricing context; the plan has not demonstrated that they are.

- **blocking, high — Canonical fold ordering cannot make an already-recorded trait line cost 0.** When a trait is purchased before any species/pack event exists in the log prefix, `fold(prefix)` has no identity event available to hoist. A shared prefix-delta helper must therefore record the trait at its cross-race price. Hoisting identity during later replays may make the final folded build sensible, but it cannot change the trait's already-frozen recorded cost. The later identity/pack event must absorb the offsetting refund, reproducing the unreadable ledger the plan says it rejects. **Suggested improvement:** require the species-setting pack event to exist before dependent purchases can be priced, or explicitly accept compensating adjustments. If identity may be selected in the form before the event is emitted, canonical replay ordering alone is not a solution.

- **blocking, high — Step 3 reintroduces the documented retroactive-refund problem rather than solving it.** A whole-build delta for a context-changing event includes every change caused by that context, not just the newly purchased component. Setting or swapping species can re-price already-owned traits from cross-race to origin/included pricing, or the reverse. Consequently, the proposed `pack` event's prefix delta may be “pack price plus/minus repricing of prior traits”, not the pack's own price. This is exactly the failure mode cited for the live sheet's hardcoded `-2` exceptions. **Suggested improvement:** first decide which contract is authoritative: pure whole-build delta, frozen component prices, or semantically accurate ledger lines. If all three are required, `compute()` needs a component-level attribution/delta interface or the event model must preserve the purchase-time pricing context used by `compute()`; a raw total delta is insufficient.

- **blocking, high — The plan has not resolved a fundamental conflict between `compute(final build)` and frozen historical pricing.** `compute(build)` prices ownership using the final build's species field. Frozen events price purchases using the context at purchase time. If species can later change, those are different pricing models even within one rules version. The equality can be forced only by assigning the resulting retroactive difference to the species-change event, which is economically a reconciliation/refund and may make the pack line misleading. Rules-version stability does not remove this conflict. **Suggested improvement:** specify species mutability and its pricing semantics. If species is immutable after dependent purchases, enforce that. If it is mutable, define whether existing traits are grandfathered, re-priced, removed, or reconciled, and then make both `compute()` and the event ledger implement that same rule.

- **blocking, high — The semantics of the new `pack` event versus the identity patch are underspecified and risk either zero charge or double charge.** Today `compute()` charges a pack solely from `b.species`. If the identity patch still sets `species`, a later pack event that does not alter relevant build state has a delta of 0. If the pack event sets `species`, then species is not merely an unpriced identity field and the identity patch must not independently set it. If both affect species/entitlement, double charging or replay ambiguity is likely. **Suggested improvement:** define the exact before/after build transformation for each event type. The cleanest stated design appears to be: the pack purchase event is the sole event that establishes or changes the species entitlement consumed by `compute()`, while the identity patch carries only genuinely unpriced fields. Test replay with each event omitted independently.

- **blocking, high — Hoisting all identity-setting events is unsafe when species can change.** With more than one identity/species event, “identity first” is not a simple dependency ordering. Hoisting a later species swap ahead of intervening trait purchases can cause those historical purchases and `_raceTraitLocked` transitions to replay under the final species rather than the species in force when bought. Stable ordering among identity events does not fix their movement across dependent events. **Suggested improvement:** distinguish initial context-establishing events from later context mutations. Do not globally hoist mutations. Define a replay model in which each purchase sees the context valid at that chronological point, and separately derive final identity state.

- **blocking, high — The telescoping proof is valid only under stronger conditions than the plan states.** It holds if: `compute(empty) = 0`; every recorded cost is calculated from the exact same deterministic fold and compute semantics; each event extends the previous prefix without mutation/removal; and no cost is later retained after an earlier prefix is edited. The described `replacePatchSlot` removes/replaces a prior slot and appends a new event. If later event costs remain frozen, their original “before” prefixes no longer match the rewritten log, so the sum need not telescope. This issue exists even within one rules version. **Suggested improvement:** formalise the proof preconditions and test them against coalescing edits. Either make corrections append-only, re-price all affected same-version suffix events, prohibit edits that rewrite historical context, or weaken the invariant to a defined checkpoint/transaction boundary.

- **blocking, high — “Append-only log” and `replacePatchSlot(log-without-this-slot)` appear contradictory.** The plan treats frozen event history as a product rule while also describing deletion/replacement of an earlier event. Without a precise distinction between draft/coalesced UI state and committed ledger history, the invariant and migration design cannot be reviewed. **Suggested improvement:** document the lifecycle: which records are provisional, which are committed and immutable, when coalescing is allowed, and whether removing a slot constitutes history rewriting. Add acceptance tests for edits made after dependent purchases.

- **blocking, high — Migration is not separable from implementation if existing logs will be replayed by the changed fold.** Even if frozen costs are left untouched, canonical reordering can change `fold(existing log)` and therefore `compute(fold(log)).total`, `_raceTraitLocked`, entitlements, and displayed state. “Grandfather versus reconciliation” is not the only migration question; replay compatibility is also at stake. **Suggested improvement:** decide migration before altering fold semantics, and include a corpus replay comparing every persisted character's pre/post final build, computed total, locks, and ledger sum. If old and new events require different replay semantics, version the event schema/fold rather than applying the new ordering universally.

- **moderate, high — Step 1 is materially the rejected ordering fix relocated into shared infrastructure.** It is stronger in scope because all writers share it, but it still relies on identity preceding dependent pricing. More importantly, as noted above, relocating ordering into replay does not ensure identity existed in the purchase prefix. The plan should not claim this distinction as sufficient justification. **Suggested improvement:** describe it honestly as a global dependency-ordering policy, identify what it fixes that writer-side ordering does not, and prove it works at event-recording time rather than only at final replay.

- **moderate, high — A single total delta cannot guarantee that the pack line displays the pack's listed price.** On a species swap, the delta may be `new pack - old pack`, or may also contain trait repricing and other species-dependent adjustments. A single net line labelled as a pack purchase may therefore show a refund, zero, or a value unrelated to `DATA.pack[newSpecies]`. **Suggested improvement:** state the ledger presentation contract. If the requirement is “each pack purchase appears at its catalogue price”, record explicit disposal/refund and purchase components, or obtain named component deltas from the rules engine. Do not label an unattributed whole-build net delta as the pack price.

- **moderate, high — Species swap verification is too narrow.** “A→B and back” does not cover traits owned before the first species, traits included by only one pack, own-species traits not included in a pack, second-origin combinations, same-price packs, pack removal, or swaps after the creation lock changes. **Suggested improvement:** add a transition matrix covering no species→A, A→B, B→A, A→none, first+second origin changes, and each relevant trait ownership category before and after the transition.

- **moderate, high — The plan asks to retire hardcoded exceptions based only on matching numbers, not matching semantics.** A recompute delta can coincidentally equal `-2` in the current fixture while still including an unintended offset that fails with a different build. **Suggested improvement:** retain or remove each exception only after tests isolate the affected component with and without previously owned dependent features. Verify attribution, not merely the final number.

- **moderate, high — “Identity” may not be the only dependency hazard, and the proposed architecture should not proceed until dependencies are enumerated.** The plan itself names level and origin class as possible price gates. A one-off identity hoist could establish a misleading precedent and require repeated global reorder rules, whose interactions may be cyclic or historically incorrect. **Suggested improvement:** inventory every field read by pricing branches and classify it as immutable initial context, chronological mutable context, or ordinary purchase state. Then choose a general event dependency model before changing fold order.

- **moderate, high — Mixed-rules-version behaviour is not merely a gate-scoping detail.** If `compute()` only knows current prices, equality to a multi-version frozen ledger is impossible unless the engine can compute under historical rules or the log carries a balancing baseline. The requested invariant therefore needs a precise domain, and tools must be able to detect whether a character is inside it. **Suggested improvement:** define an explicit status such as “reconciled single-version ledger” versus “historical mixed-version ledger”; define what totals each UI may compare; and test that no invariant warning is shown for an intentionally non-comparable character.

- **moderate, high — The new invariant test is under-specified and could pass while the real defect remains.** “A freshly built character” could be a trivial build whose events have no context dependencies. It also does not ensure every individual line is semantically correct, which is a stated reason for rejecting the cheaper alternative. **Suggested improvement:** make Anders (or an equivalent minimal reproduction) a named fixture with exact expected event labels, frozen costs, ordering, folded build, `compute().total`, and sum. Add a separate per-line assertion that included traits are 0 and the pack line equals the intended pack charge—not just that totals match.

- **moderate, high — The acceptance criteria do not say whether the target after the fix remains 33 AP.** “Frozen spend must equal `compute().total`” can pass if both values move incorrectly. The version-bump rule protects expected compute fixtures only if the relevant fixture exists and is asserted. **Suggested improvement:** state the expected Anders total and expected ledger decomposition explicitly. If `compute()` is intended to remain unchanged, require `compute().total == 33`, rules version unchanged, and the ledger sum `== 33`.

- **moderate, high — The plan needs explicit invariants for deletions, undo, replacement, and failed transactions.** Purchases are discussed, but a builder usually supports removing traits, changing species, undoing edits, and coalescing form changes. A partial write that sets identity but fails to append the pack event could leave state and ledger inconsistent. **Suggested improvement:** define atomic transactions containing all events for a logical edit, with rollback on failure. Add tests for buy/remove/undo/redo and interrupted identity/pack updates.

- **moderate, low — Second-origin charging may require more than “each species emits a pack event”.** The text says `compute()` doubles a charge for a second-origin species, but it is unclear whether the second pack has the same price, whether duplicate species are legal, and how traits included by either pack are attributed. **Suggested improvement:** specify exact first-origin and second-origin event transformations and expected ledger lines, including add, replace, remove, and duplicate prevention.

- **moderate, high — The task should be split into a semantics decision and an implementation task.** The unresolved questions are architectural/product decisions, not implementation details: mutable-species behaviour, historical replay, pack-line attribution, and migration. Implementing shared fold ordering before resolving them risks baking in the wrong model across three tools. **Suggested improvement:** first complete a short design decision task that defines event semantics, dependency chronology, and migration. Then implement engine support and writer consolidation, followed by UI display tasks. The currently out-of-scope history display bug can remain out of scope, but a machine-readable inspection of pack events is load-bearing for tests even if the final UI is not changed.

- **minor, high — `engine-parity.html` reporting 24/0 is necessary but not sufficient.** Existing output parity can remain green while recorded costs, replay chronology, or migrated characters are wrong. **Suggested improvement:** keep the 24/0 gate, but add dedicated ledger-invariant, event-attribution, chronology/ratchet, and migration-corpus gates with named expected outcomes.

- **minor, high — The empty-build assumption is easy to close and is correctly called out.** The telescoping baseline must either be confirmed as 0 or included explicitly as `sum = compute(final) - compute(empty)`. **Suggested improvement:** add a direct test before implementation and state the observed value in the amended plan.

## Solid points

- Treating `compute()` as the rules-pricing authority and rejecting independent duplicated price tables is sound.
- Preserving frozen prices across rules-version changes is a clear and valuable product constraint.
- Requiring both tools to use shared pricing infrastructure is directionally correct; the problem is that a whole-build total delta is not enough to provide semantic component attribution.
- The plan correctly identifies `_raceTraitLocked`, species swaps, double charging, and migration as serious risks. They need decisions and stronger tests, not removal from the risk list.
- The rule “bump the rules version only if `compute()` output changes” is objectively checkable, provided the expected Anders total and output fixtures are explicitly pinned.

## Assessment of the cheaper alternative

The “cross-race trait prices followed by an identity refund” alternative is structurally simpler and does satisfy total telescoping when the log is a true immutable prefix sequence and `compute(empty) == 0`. However, it fails the owner's explicit requirement that packs appear as meaningful purchases, and it preserves misleading line attribution. It is therefore not better **if semantic ledger lines are a firm product requirement**. The current proposal does not yet improve on it, because its pack event can still absorb retroactive trait repricing. A genuine improvement requires either chronological context to be established before dependent purchases or component-aware pricing from the engine.

## Required decisions before implementation

1. Is species immutable after any species-priced trait is bought? If not, exactly how are existing traits treated on a species change?
2. Is a pack ledger line required to equal its catalogue pack price, or may it be a net reconciliation delta?
3. Which event is the sole owner of the `species` state transition: identity patch or pack purchase?
4. Are coalesced patches provisional edits or committed append-only history?
5. How are existing logs replayed without changing their final state or ratchet outcomes?
6. What exact event decomposition and totals are expected for Anders, including the required post-fix total of 33 AP if `compute()` is unchanged?
